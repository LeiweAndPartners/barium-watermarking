# Algorithm Specification: Kirchenbauer Green-List Watermarking

*The specification the Phase 3 implementation follows, extracted from arXiv:2301.10226 §2 ("A Watermark for Large Language Models", Kirchenbauer et al., ICML 2023) and the reference implementation at `jwkirchenbauer/lm-watermarking`. Written before any detector code lands, per `build-plan.md`. Every section cites its source.*

## Overview

The scheme partitions the vocabulary into a "green list" and a "red list" using a key. During generation, green tokens are biased upward (the soft rule). Detection re-derives the green lists from the key alone and counts green tokens in the text, then computes a one-proportion z-score against the fair-coin expectation. No model access is needed for detection: just the key and the vocabulary.

## Seed derivation from the previous ngram

Source: arXiv:2301.10226 §2; `watermark_processor.py` (`WatermarkBase._seed_rng`, `simple_1` scheme).

The `simple_1` seeding scheme derives the seed from the single previous token:

$$\text{seed} = h \cdot t_{i-1}$$

where $h$ is the hash key and $t_{i-1}$ is the token id immediately before the position being scored. The reference implementation multiplies the hash key by the previous token id and seeds a `torch.Generator` with the product (`_seed_rng`: `input_ids[-1].item() * self.hash_key`).

Barium follows the same construction with a user-supplied key in place of the reference default. The first token of a text has no predecessor, so scoring starts at the second token: with a context width of 1, a text of $T$ tokens yields $T - 1$ scored positions.

## Hash construction

Source: `watermark_processor.py` (`WatermarkBase.__init__`, `hash_key` parameter).

The reference implementation uses a fixed large prime as the hash key:

```python
hash_key: int = 15485863,  # just a large prime number to create a rng seed with sufficient bit width
```

The key's role is to make the green/red split unpredictable without knowing it: the same key and the same previous token always produce the same seed, and different keys produce unrelated splits. Barium treats the key as per-deployment secret material generated by `barium.keygen` (see below) and never hardcodes the reference default.

## PRNG choice

Source: `watermark_processor.py` (`_get_greenlist_ids` uses `torch.randperm(vocab_size, generator=self.rng)`).

The reference implementation seeds `torch.Generator` and draws a full permutation of the vocabulary with `torch.randperm`. Barium is stdlib-only, so it uses `random.Random(seed)` — the Mersenne Twister — seeded with the same seed construction, and draws the permutation with `random.Random.sample(range(vocab_size), vocab_size)`.

Two properties matter and both hold:

1. **Determinism.** The same seed produces the same permutation on any platform, so a detector with the key re-derives exactly the generator's green lists. `random.Random` is deterministic across Python versions for `sample` on a range.
2. **Unpredictability without the key.** The permutation is uniform over vocabulary orderings for an attacker who does not know the seed. Mersenne Twister is not cryptographically secure, but the seed is derived from a secret key times a public token id; the security property the scheme needs is key secrecy, not PRNG cryptographic strength. Key material itself comes from `secrets` (see Key generation).

## Green-list size

Source: arXiv:2301.10226 §2; `watermark_processor.py` (`_get_greenlist_ids`: `greenlist_size = int(self.vocab_size * self.gamma)`).

The green list is the first $\lfloor \gamma V \rfloor$ entries of the seeded permutation, where $V$ is the vocabulary size and $\gamma$ is the green-list fraction:

$$G_i = \text{perm}_i\left[0 : \lfloor \gamma V \rfloor\right]$$

The reference default is $\gamma = 0.5$: half the vocabulary is green at each position. Under the null (text generated without knowledge of the key), each scored token is green with probability $\gamma$ — the fair-coin expectation the z-test compares against.

## The z formula

Source: arXiv:2301.10226 §2; `watermark_processor.py` (`WatermarkDetector._compute_z_score`).

Let $G$ be the number of green tokens counted and $T$ the number of scored positions. Under the null hypothesis (unwatermarked text), $G \sim \text{Binomial}(T, \gamma)$, approximated by a normal:

$$z = \frac{G - \gamma T}{\sqrt{T \gamma (1 - \gamma)}}$$

The reference implementation computes exactly this (`numer = observed_count - expected_count * T; denom = sqrt(T * expected_count * (1 - expected_count))`). The p-value is the upper tail of the standard normal, $p = 1 - \Phi(z)$ (`_compute_p_value` uses `scipy.stats.norm.sf`; barium uses `math.erfc(z / sqrt(2)) / 2`, which is the same quantity in the stdlib).

**Honesty framing (binding):** the z-score is a false-positive rate, not a certainty percentage. A threshold of $z = 4$ means unwatermarked text exceeds it with probability about $3 \times 10^{-5}$ — the rate at which the detector flags human text, not a measure of how certain a flag is. The prosecutor's fallacy applies: $P(\text{flag} \mid \text{human})$ is not $P(\text{human} \mid \text{flag})$.

## Length and the 25-token caveat

Source: arXiv:2301.10226 §1 ("detectable from short spans of tokens (as few as 25 tokens)"); Appendix G (low-entropy text yields weak detection statistics).

The signal grows with $\sqrt{T}$: at $T = 25$ scored positions a fully green text reaches $z \approx 7$, but real watermarked text is only partially green, and low-entropy text (prescriptive answers, code, factual completions) caps the achievable green rate because the model has little freedom to prefer green tokens. Short or low-entropy text carries no reliable signal. The detector reports an inconclusive verdict below a minimum scored length rather than a low-confidence flag; the exact minimum is calibrated in Phase 5.

## The demo embedder's bias rule

Source: arXiv:2301.10226 §2 (Algorithm 2, the "soft" rule); `watermark_processor.py` (`_bias_greenlist_logits`: `scores[greenlist_mask] = scores[greenlist_mask] + greenlist_bias`).

During generation, the logits of green tokens are boosted by a fixed additive bias $\delta$ before sampling:

$$\text{logits}'_v = \text{logits}_v + \delta \cdot \mathbb{1}[v \in G_i]$$

The reference default is $\delta = 2.0$. As $\delta \to \infty$ the watermark transitions from "soft" to "hard" (nearly all tokens green, at a generation-quality cost). Barium's demo embedder (Phase 4) implements the same rule over candidate next-token probabilities: it selects the highest-probability green candidate rather than adding to logits, because it ships no language model — it biases a supplied candidate distribution toward the green list. It is a labelled reference demo, not production generation.

## Key generation

Source: `watermark_processor.py` (`hash_key` default); `code-standards.md` (`secrets` for all key material).

Keys are integers drawn from `secrets.randbits(31)`, giving a key space of $2^{31} \approx 2.1 \times 10^9$ values — large enough that accidental key collision between deployments is negligible, small enough that keys stay readable in configuration. The keygen refuses to emit the reference implementation's default key (15485863) and any known shared default; a validation function refuses keys outside the documented space and known defaults. No hardcoded keys appear anywhere in the package.

## Tokenisation strategy

Source: `demo_watermark.py` (`detect` requires the generation-time tokenizer); barium's stdlib constraint.

The reference implementation scores token ids produced by the generation-time tokenizer. Barium ships no tokenizer and no model, so it defines its own whitespace-and-punctuation tokenisation: text is lowercased and split on whitespace, with leading and trailing punctuation stripped from each token. The strategy is documented in the detector module docstring and is deterministic, so the same text always produces the same token sequence and the same z-score. The consequence is stated plainly: barium detects watermarks generated and detected with barium's own tokenisation, and text watermarked with a different tokenizer's token ids is out of scope for the round-trip guarantee.

## Detection result

`DetectionResult` carries: the number of scored positions $T$, the green count $G$, the green fraction, the z-score, the p-value, the threshold used, and a verdict (`watermarked`, `not_watermarked`, or `inconclusive` below the minimum length). The verdict is a hypothesis-test outcome at the configured threshold, not a confidence percentage.
