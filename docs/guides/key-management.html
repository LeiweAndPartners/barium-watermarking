Key management

Back to the README · The paper (arXiv:2301.10226 §2) · The threat model

The key is the whole secret. The same key derives the green lists at generation and re-derives them at detection, so the key is the attack surface: if it leaks or is inferable, attackers spoof or evade.

Barium draws keys from secrets.randbits(31), giving a key space of 2³¹ ≈ 2.1×10⁹ values — large enough that accidental collision between deployments is negligible, small enough that keys stay readable in configuration. Key material comes from secrets, never random.

Known defaults are refused on both the emit and the accept path. The reference implementation ships a hardcoded hash key, 15485863 — a key that appears in a public repository is not a secret, and a split derived from it is predictable. Barium refuses to emit it and refuses to accept it.

Try it: generate keys, and try the reference default.

—

The key space is [1, 2³¹−1]. Zero is excluded so a key is always truthy and a missing key cannot masquerade as a valid one. The key is per-deployment secret material: the same key must be used at generation and detection, or the round-trip fails.

The trade-off: a public key means anyone can verify — and anyone can spoof. A private key means detection runs behind your own API — and third parties can no longer verify. Both modes are legitimate; the choice is yours. See the threat model for the spoofing and evasion surface.
